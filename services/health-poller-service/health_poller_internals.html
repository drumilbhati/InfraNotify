Step-by-step explanation of how the health poller works internally in PulseBoard

1 — Scheduler wakes up
2 — Fetch services
3 — Ping in parallel
4 — Publish to Kafka
5 — Alert engine reacts
Every 30 seconds, Spring wakes up the poller
You write one method and annotate it with @Scheduled. Spring's task executor calls it automatically on the interval you set. You don't write a while loop, you don't manage threads. It just runs.
@Component public class HealthPollerJob { // Spring calls this every 30,000 milliseconds automatically @Scheduled(fixedRate = 30000) public void runPollingCycle() { // everything below happens once per cycle log.info("Polling cycle started"); } }

You also need @EnableScheduling on your main class. Without it, Spring ignores all @Scheduled annotations silently — a common gotcha.

It asks auth-service: what services should I ping?
The health poller doesn't have its own database. It calls auth-service via REST to get the list of all active registered services and their endpoint URLs. This is the only cross-service REST call in the whole cycle.
@Autowired private WebClient webClient; List<MonitoredService> services = webClient .get() .uri("http://auth-service:8081/internal/services/active") .retrieve() .bodyToFlux(MonitoredService.class) .collectList() .block();
Why WebClient and not RestTemplate?
RestTemplate is blocking — it holds one thread per request until the response comes back. If you're pinging 200 services, that's 200 threads sitting idle waiting. WebClient is non-blocking — it fires all 200 requests and handles responses as they arrive, using a tiny thread pool. Night and day for performance.
It pings all services at the same time — not one by one
If it pinged services sequentially, 200 services × 5s timeout = potentially 1000 seconds per cycle. Instead it fires all requests in parallel using a thread pool, collects results, and moves on.
ExecutorService pool = Executors.newFixedThreadPool(20); List<Future<PingResult>> futures = services.stream() .map(service -> pool.submit(() -> pingService(service))) .toList(); // Collect all results (waits for the slowest one) List<PingResult> results = futures.stream() .map(f -> f.get()) .toList(); private PingResult pingService(MonitoredService service) { try { long start = System.currentTimeMillis(); int status = webClient.get() .uri(service.getEndpointUrl()) .retrieve() .toBodilessEntity() .timeout(Duration.ofSeconds(5)) // give up after 5s .map(r -> r.getStatusCode().value()) .onErrorReturn(0) // 0 = unreachable .block(); long responseMs = System.currentTimeMillis() - start; boolean isUp = status >= 200 && status < 300; return new PingResult(service.getId(), isUp, responseMs, status); } catch (Exception e) { return new PingResult(service.getId(), false, -1, 0); } }

Each result becomes a metric event on Kafka
The poller doesn't decide if an alert should fire — that's the alert engine's job. The poller just packages each ping result as a standard metric event and publishes it to the health.checks Kafka topic. One event per service per cycle.
results.forEach(result -> { MetricEvent event = MetricEvent.builder() .serviceId(result.getServiceId()) .metricName("endpoint_health") .value(result.isUp() ? 1.0 : 0.0) // 1 = up, 0 = down .unit("status") .tags(Map.of( "status_code", String.valueOf(result.getStatusCode()), "response_ms", String.valueOf(result.getResponseMs()) )) .timestamp(Instant.now()) .build(); kafkaTemplate.send("health.checks", result.getServiceId(), event); });
Why value 1.0 and 0.0?
The alert engine works with numbers, not booleans. A rule looks like "if endpoint_health is less than 1.0 for 60 seconds, fire an alert." This means your alert rules for uptime use the exact same system as CPU or memory rules. One rule engine, all metric types.
Alert engine picks it up and decides what to do
The alert engine is subscribed to the health.checks topic. Every event that comes in gets evaluated against the service's alert rules. It tracks state in Redis — so it knows whether this service was already down last cycle or if this is a fresh outage.
@KafkaListener(topics = "health.checks") public void onHealthCheck(MetricEvent event) { // Fetch rules for this service (cached in Redis for 60s) List<AlertRule> rules = ruleCache.getRulesForService(event.getServiceId()); for (AlertRule rule : rules) { if (!rule.getMetricName().equals(event.getMetricName())) continue; boolean breached = evaluate(event.getValue(), rule); // e.g. 0.0 < 1.0 → true String stateKey = "alert:state:" + rule.getId(); String currentState = redis.get(stateKey); // "OK" or "FIRING" if (breached && !"FIRING".equals(currentState)) { redis.set(stateKey, "FIRING"); kafkaTemplate.send("alerts.fired", buildAlertEvent(event, rule)); } else if (!breached && "FIRING".equals(currentState)) { redis.set(stateKey, "OK"); kafkaTemplate.send("alerts.resolved", buildAlertEvent(event, rule)); } // if already FIRING + still breached → do nothing (no spam) } }

The Redis state key is what prevents notification spam. Without it, every 30-second poll of a down service would send a new alert email. With it, you get exactly one alert when it goes down, and one when it recovers.
